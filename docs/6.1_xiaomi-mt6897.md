# 6.1, xiaomi mt6897

Xiaomi 14T (`degas`), Dimensity 8300-Ultra, on a prebuilt GKI
`6.1.176-android14-11`. The port controller is a Richtek mt6375 sitting on
i2c-5, which is the same part the 17T Pro and the 15T Pro carry, so the whole
of this is the ordinary case rather than a special one.

Nothing here is about the kernel being short of anything - `caps_info` has the
objects, `pe_ready` has the contract, and both read correctly the moment the
labels are right. What took three attempts was the labelling, and the three
things that went wrong are the reason README.md's rules are written the way
they are.

## What it looks like before any of that

```
u:object_r:sysfs:s0             /sys/class/tcpc
u:object_r:sysfs:s0             /sys/class/tcpc/type_c_port0
u:object_r:sysfs_usb_nonplat:s0 /sys/class/typec
u:object_r:sysfs:s0             /sys/class/typec/port0
u:object_r:sysfs_batteryinfo:s0 /sys/class/power_supply/usb/real_type
```

Both class entries are symlinks into the platform device of whatever carries
the port, and those are what a genfscon has to name:

```
/sys/class/tcpc/type_c_port0 -> /sys/devices/platform/11f01000.i2c/i2c-5/5-0034/11f01000.i2c:mt6375@34:tcpc/tcpc/type_c_port0
/sys/class/typec/port0       -> /sys/devices/platform/rt-pd-manager/typec/port0
```

## The class directory needs the label too

Labelling only `.../mt6375@34:tcpc/tcpc` gets a screen that says the interface
was not found, with **no denial anywhere in the log**.

`TcpcSource.present()` lists `/sys/class/tcpc` to find the port. Listing a
directory needs `read`; walking through one needs only `search`, and
`system/sepolicy/private/domain.te` already grants every domain `search` on
generic `sysfs`. So the open never happens, `File.list()` returns null, the
source reads as absent, and the policy looks correct because nothing complained.

```
genfscon sysfs /class/tcpc   u:object_r:sysfs_tcpc:s0
```

The `wakeup` entries a MediaTek device tree usually already has under
`.../mt6375@34:tcpc` are not disturbed by the subtree entry - genfscon takes
the longest matching prefix, so they keep `sysfs_wakeup`.

## The type-C class cannot be relabelled

MediaTek's base policy carries

```
genfscon sysfs /class/typec   u:object_r:sysfs_usb_nonplat:s0
```

and a second genfscon for one path does not build. The grant has to name the
vendor's own type:

```
allow system_app sysfs_usb_nonplat:dir r_dir_perms;
allow system_app sysfs_usb_nonplat:file r_file_perms;
```

`TypeCClass.port()` lists the class directory as well as reading out of it - a
partner device appearing beside the port is how it knows something is attached
- so `search` is again not enough.

## Relabelling takes the subtree from the USB HAL

`/sys/devices/platform/rt-pd-manager/typec` is generic `sysfs` on a stock
policy, which every domain may walk. Giving it a type of its own stops the ones
that were relying on that, and on this board that is `mtk_hal_usb`:

```
avc: denied { search } for comm="android.hardwar" name="typec"
     scontext=u:r:mtk_hal_usb:s0 tcontext=u:object_r:sysfs_tcpc:s0 tclass=dir
```

It is not only reading. `android.hardware.usb-service.mediatek` writes
`power_role`, `data_role` and `port_type` under that directory to swap roles,
and `init.mt6897.usb.rc` chmods those three to 664 for the system group, so the
HAL wants read and write back:

```
allow mtk_hal_usb sysfs_tcpc:dir r_dir_perms;
allow mtk_hal_usb sysfs_tcpc:file rw_file_perms;
```

With that in, `dumpsys usb` reports the port and its supported role
combinations again.

## What the screen reads

With a plain data cable to a PC - nothing that speaks power delivery:

```
selected_cap = 0
local_src_cap(type, vmin, vmax, oper)
local_snk_cap(type, vmin, vmax, ioper)
0 5000 5000 3000
3 3600 10000 5000
remote_src_cap(type, vmin, vmax, ioper)
remote_snk_cap(type, vmin, vmax, ioper)
pe_ready: no
```

so the charger's list is absent and the only objects on screen are the phone's
own sink capabilities. They are there whether or not anything is plugged in,
which is worth saying on the screen rather than leaving to be inferred: the
section is headed for the port, not for the charger.

With a 60 W adapter that offers five fixed objects and no programmable supply:

```
selected_cap = 1
remote_src_cap(type, vmin, vmax, ioper)
0 5000 5000 3000
0 9000 9000 3000
0 12000 12000 3000
0 15000 15000 3000
0 20000 20000 3000
pe_ready: yes
real_type: USB_PD
```

which the app shows as a contract in force, five offered objects and object 1
in use. The battery was full at the time, which is why the position in force is
the 5 V one and the charger is delivering 5.05 V at 0.45 A rather than anything
near its limit.

## What this board's sink table says

```
0 5000 5000 3000      fixed, 5V 3.0A
3 3600 10000 5000      programmable, 3.6-10V 5.0A
```

One fixed object and one augmented one. There is no fixed 9 V or 12 V here, and
that is not a row going missing: above 5 V this phone takes power delivery
through the programmable supply, 10 V at 5 A being 50 W, and the 67 W it
advertises is Xiaomi's own protocol rather than anything in the power delivery
specification.

A fixed object carries one voltage by definition - `tcpci_core.c` prints
`vmin` and `vmax` from the same field, so they are equal - which is why only
the programmable row comes out as a range.

## What is still missing, and why

The charger section and the measurement. `/sys/class/power_supply/usb/*` is
`sysfs_batteryinfo`, and `system/sepolicy/private/domain.te` neverallows that
for every coredomain but a handful of which `system_app` is not one. The
sideloaded build has them; the ROM build cannot, and nothing on the screen
depends on them.
